# Pivot 下一阶段计划：单刊编辑日常助手与试用验证

整理日期：2026-11-14。状态：规划，未开始实现。本轮只读核对仓库、PR 状态和官方业务文档，不操作 VPS、数据库、原件、模型凭据或邮件。

## 建议目标

让一位获授权编辑在一本期刊中，独立完成“询问本人待办 → 打开稿件 → 核对资料或修回 → 查看准确依据 → 负责人确认”的日常闭环，并通过实际编辑评价判断是否值得继续投入。

近期产品定位继续是原投稿系统旁的辅助审阅工具。已有正式流程样本用于验证工作流与权限，不以这一阶段替换期刊现行投稿系统。保持对话处于主体位置，材料与表单按当前稿件展开，不增加第二套传统管理控制台。

## 里程碑一：有事实依据的日常待办问答

预计 4—5 个有效开发日，包含代码、测试、修复和审查；按实际发现调整。

支持的问题限定为：

- “我今天需要处理什么？”
- “本周哪些任务到期，哪些已经逾期？”
- “这篇稿件现在到哪一步，轮到我做什么？”
- “这个任务为什么显示在我的待办里？”

优先以结构化查询完成日期与身份判断，模型只组织措辞。今天按用户明确使用的 IANA 时区，本周暂定周一至下周一半开区间，并显示实际日期范围；逾期依据读取时刻。本人角色不自动汇总其他身份，切换身份后重新读取。

回答的任务事实最少绑定 task_id、manuscript_id、实际任务类型/状态、due_at 或未设、读取时刻、时区及可授权打开的稿件链接。稿件状态另来自实际工作流投影；当前版本或任务修订标识按既有模型提供，不为了本功能复制一份可编辑状态。多页结果必须说明当前范围并支持继续读取，不能把第一页说成全部待办。

不把排序分数称为学术重要性。初始仅使用确定规则：逾期、当日到期、未来已设日期、未设日期；同组稳定排序。质量问题可以引用已有保存证据提示，不据模型猜测擅自改变期限或业务优先级。

实现边界：

- 抽取可复用的只读服务和日期处理，由日历路由与 chat 消费；不让 chat 调用 HTTP 路由函数，不复制授权 SQL。
- 复用实际身份/归属/分派、匿名题名及会话重验；网络等待后与保存回答前重新检查。
- 待办会变化，历史回答明确是当时快照；重新查看当前事实需重新查询。保存历史涉及的多稿件/任务可见性必须与既有历史授权机制衔接，撤权后不得通过旧回答泄露。
- 不新增改期、完成任务、发信、确认、决定工具。私人物料没有正式任务时，说明“尚无正式流程关联”，仍可做资料问答。
- 界面继续使用中心对话与既有左下角日历；不增加重复的工作清单页面或装饰性说明。

验收：相同身份/时区/查询时刻下对话与日历任务事实一致；覆盖零任务、未设日期、跨月/年、DST、分页、旧任务、身份切换、撤权、推理中任务完成/重分派与迟到响应。作者、审稿人、编辑、主编测试各自范围，不以主编身份获得他人私有待办。

## 里程碑二：验证资料核对和修回核对的实际质量

预计 4—6 个有效开发日，公开材料搜集和许可等待另外记录。

保持两个核心任务：A，导入后核对作者/机构/ORCID 原文线索、正文覆盖和缺项；B，按具体要求核对作者回应、正文落实和编辑充分性。

先复用 6 篇/42 项准备包，不从中推算全学科准确率。争取补齐至少 2 套许可明确的“原稿＋修订稿＋审稿意见＋完整逐点回复”材料；至少覆盖一份真实原生 DOCX 和文本层 PDF。取得不到时保留明确阻塞，缩小修回评价范围，不能用修订说明节选或生成文本冒充完整回复。

逐项保留许可、来源 URL、文件 SHA、版本、提取方式、页/段/字符定位及材料覆盖。先人工确定参考，再运行 AI；已经用于调试的题目与新保留材料分别标记。一个复合要求中的多个分句都要核对，不以局部修改证明整项完成。

重点评估并修复：作者错配、提取遗漏、读错版本、引文位置正确但语义不支持、只回应而正文未改、部分修改被判整项完成、材料不足却声称全文未修改。模型拒答和待核对同样计入覆盖，不通过一律拒答制造高准确率。

真实 DeepSeek 回归只在安全环境中存在有效凭据且材料许可允许时执行；固定模型 ID deepseek-flash，真实失败显式记录，不降级 Mock 冒充成功。保存模型/参数/源码/材料版本、用量、延迟、失败、返工和费用；未知用量或成本留空。历史模型通过不证明当前凭据仍可用。本次规划没有发起调用。

验收：全部评测项有分母、结果、引用及人评状态；错版引用、越权泄露和无依据判整项完成等严重问题修复并重测后才进入下一关口。小样本“观察到 0 个严重问题”不能声称真实错误率为零。

## 里程碑三：实际编辑试用与工程交付

预计 2—4 个有效开发日用于准备、反馈修复与报告；人员排期另计。目标是 2 位获授权编辑独立执行核心任务，先使用合成或许可公开材料，不自动联系人员。

沿用现有单刊评价协议和回传，不新建评价平台。记录独立标注、分歧、查证与改错时间、模型等待、失败恢复、采用程度和继续使用意愿。人工方式与 Pivot 使用难度相近的材料、交替顺序，避免同篇先读后测造成虚假提效。

阶段继续投入的判断：

- 主要任务可以完成，严重权限/错版/无依据完成问题修复后复查。
- 编辑能指出哪些结果可采用、哪些需要重做，具备真实引用和原始评价记录。
- “净耗时减少约 25%”和“两位编辑愿意继续使用”沿用为探索性目标，不是已测结果或行业标准。两人样本不足以推断普遍效果。
- 连续两轮仍不节时或多数结果需重做时，收窄到表现较好的任务，暂停低效功能扩张。

暂时只有产品经理本人试用时可以完成工程及自测报告，但实际编辑评价保持未完成，不以 Codex 或同一人多次填写替代。

## 专业工程师复核与放行

采用明确问题清单和复现材料委托复核，结论由实际工程师给出。以下六包沿用 SECURITY.md，不由模型审查代签：

1. PDF/ZIP/XML 攻击面、解析隔离、资源上限及文件权限。
2. 用户/期刊/职务/分派/历史消息/下载的对象授权及撤权。
3. 版本、原件摘要、确认快照、幂等、并发与迁移保留。
4. 模型出域内容、供应商设置、凭据、日志与材料授权。
5. PostgreSQL＋原件一致备份、新环境恢复、回滚和可用性。
6. 2.5GB 目标配置的内存/磁盘/并发、TLS、账户、安全更新和运维责任。

公开材料的本机试用可以先行。涉及未公开稿件、机构账号、扩大公网访问或正式业务之前，必须取得对应的授权与复核结论。VPS 操作继续需要单独部署授权；本计划不是放行或自动部署指令。

## 时间、分工与依赖

单人＋Codex 预计 10—15 个有效开发日，另留 3—5 个修复缓冲日，约 3—4 周工程窗口；材料许可、编辑排期、专业复核和机构审批不包含在内，不能保证固定日历日完成。

产品经理负责选择单刊任务、安排真实编辑、确认参考标准与取舍；Codex负责受控实现、测试、证据整理和修复；实际编辑负责独立判断；专业工程师负责上述边界复核。无需先扩为完整五人研发团队，但真实评价和专业复核不能由“一个人＋Codex”自行认证。

本次只核对 PR #12，保持草稿未合并。执行里程碑一时明确分支基线：如仍未授权合并，就从已验收的日历分支建立依赖分支并记录依赖，不假设日历已进 main。每一技术片单独 PR、固定源码与实际结果，不在最后堆成不可审查的大改。

## 工程验收和资料交付

- 每片先针对真实失败补回归，再运行适当 API、界面与边界检查；代码交付前在隔离 Mock 环境运行 scripts/verify.sh，并核对最终提交 CI。
- 不删除测试、不提高重试掩盖问题、不清原库；静态 Demo、隔离应用、现有主服务与 VPS 分开记录。
- 当前 1,666 后端＋540 浏览器是上一阶段的基线，不是本计划的新执行结果，也不是以增加用例数为目标。
- 交付目标包括：日常问答演示脚本、源码/来源与权限合同、精确提交的回归报告、许可材料索引、实际人评与耗时报告、专业复核问题清单、已知限制及是否继续试用的决定。
- EMAIL_SEND_ENABLED=false；邮件无真实发送。重大决定、资料确认和作者声明继续由当前有权负责人在独立页面核对后确认。

## 暂缓内容及后续顺序

本阶段不做：多刊/跨刊中心、邮箱或 ORCID 注册/OAuth、人物主数据合并、自动催审、真实邮件、自动查重、OCR、全面语义搜索、自治长期 Agent、正式 DOI/公开出版、重写微服务。现有 ORCID/DOI 链接不提升为身份认证或全文科学认证。

如试用通过，先按实际阻断反馈推进负责人受控改期与历史审计，或结构化外部投稿来源；然后沿原六阶段路线扩展。只有日历需求得到证实时才做改期，不因有日期字段就自动添加提醒服务。

## 本轮重新查阅的官方业务参考

- [OJS 3.5 评审阶段官方文档](https://github.com/pkp/pkp-docs/blob/main/learning-ojs/editorial-workflow/en/review.md)：区分邀请回应期限与报告期限，按评审状态组织工作，选定评审文件，编辑确认与决定分开。采用这些业务边界，不照搬所有后台界面或角色放宽方式。
- [Janeway 编辑评审指南](https://janeway.systems/pages/support/guides/editor-guide-to-review.html)：评审轮次、选定文件、邀请响应与审稿工作分层。继续使用轮次/版本/实际分派，不把稿件压成一个可任意修改的标签。
- [Janeway 截止期提醒](https://janeway.systems/pages/support/email-and-reminders/scheduling-reminders.html)：邀请、已接受评审、修回分别关联期限。Pivot复用这种职责区分；自动邮件提醒仍受本项目禁发与逐封人类审批边界限制。

上述建议是结合官方流程与现有源码的工程取舍，不代表这些平台为 Pivot 的实现、质量或安全提供背书。
