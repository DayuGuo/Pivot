# 从 OJS 工作流提取的后端规则

这里先写固定来源的观察，再写Publishing OS选择。来源：本目录sources/pkp-docs的submission/review/production指南（frontmatter3.5），PKP ReviewRound/ReviewAssignment/Decision/StageAssignment实现与安装迁移，均由manifest固定SHA。不是对任意生产OJS站点的行为保证。

## 上游观察

**投稿与分派**：新投稿进入Submission阶段，可以自动或人工分派编辑。期刊角色组、角色可访问阶段和某稿件的实际分派分别存储。分派中的recommend_only区分只能建议的编辑和能作正式决定的编辑；编辑可改元数据也是独立开关。这比一个用户表上的role字符串细。

**审稿准备**：官方review指南先要求选择适合评审的文件并确保匿名化，再邀请审稿人；回复期限与报告期限分开。系统隐藏身份不代表文件内容/属性已匿名化。`review_round_files`与`review_files`支持按轮次、按审稿人授权具体文件。不能把“当前稿件的所有附件”作为审稿人默认下载集合。

**并行与状态投影**：一轮会有多个review_assignments，各自可能等待回应、已接受、拒绝、取消、已提交、已被编辑确认或逾期。ReviewRound根据这些分派和编辑决定推导轮次状态，READY与COMPLETED有区别。一个审稿人完成不能自动代表整篇稿件可以决定；已邀请人数也不等于有效报告数。

**报告与作者可见性**：review_forms/elements/responses支持结构化问题；报告与编辑确认分开。在作者能看到哪些意见之前需要执行发布/可见性规则，不能把所有内部审稿文本序列化给作者。review_files决定可读原稿，submission_comments的viewable、评审表配置及应用层共同影响内容可见性，单看某个列不足以完成匿名化。

**修回**：Request Revisions可以要求或不要求新一轮评审；新轮次可另开。指南特别提醒先让作者上传修回，再建立新的review round，以免修回文件归错轮次。ReviewRound模型根据相关决定之后是否上传修订判断“修订已提交”，不是只信一个客户端按钮。

**决定**：Decision类型绑定阶段；Repository校验当前稿件与决定阶段一致、review round合法，并区分recommendation与实际decision。edit_decisions保存独立记录。ACCEPT移动到copyediting，SEND_TO_PRODUCTION是另一动作；决定状态与作者/审稿人通知也是不同事实。指南中的某些动作会发送通知，Publishing OS不继承自动外发语义。

**制作与出版**：Production阶段准备最终格式galley、元数据和校样。作者可参与确认最终校样，publication/galley approval、排入issue、真正published与通知读者不是同一个布尔值。一个publication可有PDF/HTML等多个呈现载体，全期galley又是另一实体。

## 本项目采用与不采用

| OJS经验 | Publishing OS落地选择 | 不照搬的部分 |
| --- | --- | --- |
| 稳定submission与publication版本分离 | 稿件身份、提交版本/作者快照、发布预览分开 | 不将publication.version直接当所有文件的版本号 |
| stage/status/round projection分开 | phase+current_step、任务实例、轮次状态投影 | 不拿任意可编辑标签控制工作流 |
| 分派与角色/建议权分开 | Membership角色集合+稿件Assignment+阶段capability | 不给所有editor全刊读取/正式决定权 |
| 文件按轮次及个人授权 | version_files、review_round_files、assignment绑定下载 | 不默认整篇稿件所有文件可读 |
| 邀请、回应、报告、确认分时刻 | invitation响应/报告分派/报告提交与复核分实体或独立状态 | 不将已发邮件/已点邀请当作已接受 |
| 决定是历史实体 | 人类确认快照、editorial_decisions与审计事务提交 | 不使用LLM学术判断自动录用/拒稿 |
| 生产、校样、galley、issue分离 | 首版本地校样/预览闭环，保留后续发布扩展 | 不声称DOI、公开发布、邮件投递已实现 |
| 标准业务阶段较粗 | 按用户要求把初审细化为预审/查重复核/材料/主编范围/编辑质量 | 不把用户要求的这些细分检查说成OJS现成列/必经流程 |

## v0.1 建议的可操作闭环

1. 作者整理草稿与字段来源，补齐期刊要求；提交到独立审核页时固定版本、作者、文件与声明摘要，由作者确认正式投稿。
2. 编辑预审、录入/查看明确标为测试或人工上传的查重证据、材料筛选；检测报告的存在与“负责人判断通过”分开。没有外部检测器时不得生成伪造相似度。
3. 主编完成范围初筛并确认责任编辑，创建具备明确责任人的质量评估任务。
4. 编辑准备一轮评审及待审文件，选择审稿人；站内邀请草稿/邀请记录先由负责人审核。真实邮件继续禁用。
5. 审稿人以本人会话接受或拒绝邀请并声明利益冲突；接受后才读被授权的匿名材料，独立审核提交自己的报告。
6. 编辑汇总公开/私密意见并提出建议，主编在独立确认页作修回或决定。编辑建议不自动终结稿件。
7. 作者提交新版本及逐点回应；旧版/旧轮次/旧确认保留，任何再次确认都绑定新输入，不能用旧报告证明新文件已核验。
8. 有权负责人确认进入制作；制作校样、作者确认、生成本地发布预览。尚未授权生产发布时终点写“本地预览就绪”，不能写成真实对外发表。

这些是本项目建议，不是声称已经实现。每一步都应有可见待办、后端事实、刷新恢复、权限拒绝、可重试但不重复生效的确认记录；中间主体对话持续可用，AI只能准备候选动作。

## 从成熟系统反推验收

- 同稿v1/v2必须能分别下载并显示原作者/文件/判断；改用户资料不改旧署名。
- 未接受邀请者不能读取评审原稿；审稿人不能查看别人私密报告；作者不能读取身份和内部意见。
- 一人拒绝邀请不使整轮拒稿；一人交报告不使全部评审完成；取消记录仍可审计。
- Editor recommend-only提交建议后仍显示“等待主编确认”，不是已录用。
- 负责人/版本/附件变化后旧proposal无法提交；同时确认只允许一次转换/下一待办。
- 文件下载按受控存储键与授权查询，不能用文件名拼接任意路径。
- 决定与邮件审批分别存在；形成决定不等于邮件已发出。测试中Mailpit不出现未经允许的新邮件。
- 生成校样/预览可核验具体内容哈希，不能只改变一个展示用status。
